PL2005: Required admission and source evidence must be complete🔗

Development documentation generated from commit d66b6ca1862f with Lean 4.34.0; linter version unreleased (no released package). Moving route: /lean-plumb/dev/rules/PL2005/. Snapshot route for this commit: /lean-plumb/rev/d66b6ca1862f…/rules/PL2005/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. Required evidence is missing, incomplete, unsupported or invalid: owned declarations did not pass kernel admission, a frozen source changed during the audit, or authentication the result needs could not complete. The result is INCOMPLETE.

Action. Remove the construction that bypasses kernel checking (or the source change during the run), then run the project command that collects the missing evidence.

What triggers it🔗

Before accepting proof evidence the checker replays every owned logical declaration and its owned dependencies through Lean's kernel (Admission.validate). A declaration that fails replay, source bytes that changed after they were frozen, or a required authentication that failed is reported here with impact incomplete.

In the editor, this rule marks results that need fresh evidence only the project command collects, and those messages name lake lint. The editor also reports it, as incomplete, when its own analysis of a declaration fails or the module has elaboration errors.

Why it matters🔗

Successful elaboration alone is not checked admission: metaprograms and debug options can store declarations the kernel never checked. An accepted result must rest on kernel-checked evidence for the exact frozen sources.

How to fix it🔗

  1. Remove uses of debug.skipKernelTC, addDecl with unchecked values, or other metaprograms that add unchecked declarations; state and prove the theorem normally.

  2. Do not edit sources while an audit runs; rerun it.

  3. For an editor pending result, run lake lint (or lake lint -- --fresh).

[VIOLATION[kernel-admission]] while replaying declaration 'reflexive':
(kernel) declaration type mismatch, 'reflexive' has type
  True
but it is expected to have type
  ∀ (n : Nat), Eq n n

Correction

Change to Example.lean:

- import Lean
- /-! Reflexivity declared with unchecked, ill-typed evidence. -/
- open Lean Elab Command
- set_option debug.skipKernelTC true in
- run_cmd liftCoreM <| Lean.addDecl (.thmDecl {
-   name := `reflexive
-   levelParams := []
-   type := mkForall `n .default (mkConst ``Nat) (mkApp3 (mkConst ``Eq [Level.succ Level.zero]) (mkConst ``Nat) (mkBVar 0) (mkBVar 0))
-   value := mkConst ``True.intro })
+ /-! Reflexivity for every natural number. -/
+ theorem reflexive (n : Nat) : n = n := rfl

The correction replaces ill-typed unchecked evidence with a checked proof of the same reflexivity statement.

Required proof shape🔗

The replayed declaration must type-check in the kernel with exactly its stated type and value.

What a passing result establishes🔗

Every owned logical declaration and its owned dependencies passed kernel replay, and the frozen sources were unchanged during the audit. A failed admission or changed source is incomplete and never accepted.

It does not establish:

  • Imported, unowned dependencies are not replayed; they remain the declared trusted base.

  • Incremental admission does not establish fresh source elaboration.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No option waives admission. A failed generated-role authentication cannot waive PL1001 or PL1006.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.
