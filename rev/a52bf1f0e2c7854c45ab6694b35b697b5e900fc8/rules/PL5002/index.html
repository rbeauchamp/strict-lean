PL5002: Registered public material declarations require docstrings🔗

Development documentation generated from commit a52bf1f0e2c7 with Lean 4.34.0; linter version unreleased (no released package). Moving route: /lean-plumb/dev/rules/PL5002/. Snapshot route for this commit: /lean-plumb/rev/a52bf1f0e2c7…/rules/PL5002/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. A public declaration registered with @[plumb_material] as evidence for a material normative claim has no docstring.

Action. Add a docstring stating the declaration's formal purpose, domain and hypotheses, result and boundary, with a labelled # Intent section (PL5003).

What triggers it🔗

The checker selects public declarations carrying the persistent @[plumb_material] registration and asks Lean for their docstrings (findDocString?, which includes inherited documentation). A registered declaration without one is rejected with applicability material-documentation.

Unregistered declarations are not selected; there is no name heuristic.

Why it matters🔗

A material claim must be readable without reconstructing it from the proof: the docstring states what the declaration establishes and under which assumptions, and binds the written intent to that exact declaration.

How to fix it🔗

  1. Add /-- … -/ immediately before the declaration, stating purpose, domain and hypotheses, result and boundary (standard §5.1).

  2. Include a # Intent section with the requirement the claim must meet (standard §5.2); a missing Intent section is PL5003.

Correction

Change to Example.lean:

  import Plumb.MaterialClaim
  /-! Reflexivity for every natural number; `reflexive` supplies its evidence. -/
+ /-- Every natural number equals itself, without additional hypotheses.
+ 
+ # Intent
+ Equality on natural numbers must be reflexive for every value, with no side condition. -/
  @[plumb_material] theorem reflexive (n : Nat) : n = n := rfl

The correction adds the registered theorem's docstring, including its # Intent section; registration, proposition and proof are unchanged.

Required proof shape🔗

No proof obligation: the rule checks presence. The docstring must describe the elaborated statement faithfully.

What a passing result establishes🔗

Every registered public material declaration has a docstring.

It does not establish:

  • That every material declaration is registered, or that the docstring is faithful and adequate (R-DOC); registration completeness is semantic review.

  • Docstrings of unregistered, private or trivial declarations, which the standard recommends but does not require.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-DOC: documentation is complete and faithful to the declarations and requirements

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option or command-line flag makes this rule pass on a claimed surface. set_option linter.plumb false and plumb.localFoundation never waive it: lake lint, the build-lint policy target and axiomGate still apply the rule. Where Plumb's local linter reports a finding during a project build (axiomGate and the policy target keep it on by default; under lake lint a source set_option linter.plumb true turns it back on), that finding is a build warning, so the result is INCOMPLETE under PL2003 instead of carrying this rule's finding. Switching the local linter off changes which finding is reported, never whether the result is accepted. Hiding the diagnostic does not establish the property it checks.

Registration is @[plumb_material] from Plumb.MaterialClaim. Removing a registration from a material declaration changes the reviewed claim, not only this rule's result.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

Lean's broader linter.missingDocs checks all public declarations; this rule deliberately covers only registered material evidence.
