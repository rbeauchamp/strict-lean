PL5001: Claimed modules require module documentation🔗

Development documentation generated from commit 56c53c2bb3ab with Lean 4.34.0; linter version unreleased (no released package). Moving route: /lean-plumb/dev/rules/PL5001/. Snapshot route for this commit: /lean-plumb/rev/56c53c2bb3ab…/rules/PL5001/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. A module in a claimed surface has no module docstring (/-! … -/ or Verso module documentation).

Action. Add a module docstring that identifies the module's material declarations and assumptions.

What triggers it🔗

When a claimed module finishes elaborating, the checker asks Lean for its module documentation. A module without any is rejected with applicability module-documentation. Empty modules are included.

Why it matters🔗

Module documentation tells a reader which declarations carry the module's claims and under which assumptions, so the claims can be reviewed without reading every proof.

How to fix it🔗

  1. Add /-! … -/ at the top of the module, after the imports.

  2. Follow the template in standard §5.3: purpose, main declarations with their results and hypotheses, assumptions and dependencies, design notes. Keep only sections that help.

Checked example🔗

Checked policy rejection: the violating input was completed by the checker and rejected with the findings below; the corrected input passed a completed positive check.

Invocation: fresh whole-project audit (axiomGate) of <example>; evidence mode freshProject; run by the qualification runner's ruleExamples entry, which executes the same detector with dependency Git facts captured once for the campaign. Violating run status: rejected; corrected run status: completed.

Violating input

Findings of the violating run

PL5001 error violation fresh project, claim kernel-only

Subject Example at module `Example`

module-documentation: add a module doc comment describing this module

Correction

Change to Example.lean:

+ /-! Reflexivity for every natural number; no additional assumptions. -/
  theorem reflexive (n : Nat) : n = n := rfl

The correction adds module documentation to the unchanged reflexivity evidence.

Required proof shape🔗

No proof obligation: the rule checks presence of documentation.

What a passing result establishes🔗

Every claimed module has module documentation metadata.

It does not establish:

  • That the documentation identifies all material declarations and assumptions, or describes them faithfully (R-DOC). Presence says nothing about content; no headings or layout are imposed.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-DOC: documentation is complete and faithful to the declarations and requirements

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

No source option, attribute or command-line flag makes this rule pass on a claimed surface. set_option linter.plumb false and plumb.localFoundation never waive it: lake lint, the build-lint policy target and axiomGate still apply the rule. Where Plumb's local linter reports a finding during a project build (axiomGate and the policy target keep it on by default; lake lint builds with it off, whatever the source sets linter.plumb to), that finding is a build warning, so the result is INCOMPLETE under PL2003 instead of carrying this rule's finding. Switching the local linter off changes which finding is reported, never whether the result is accepted. Hiding the diagnostic does not establish the property it checks.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.

Limitations and unsupported cases🔗

The editor reports this rule only when the module has finished elaborating without errors; a module with elaboration errors gets PL2005 (incomplete) instead.
