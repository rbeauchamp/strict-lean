PL2001: The declared Lean environment must be available🔗

Development documentation generated from commit 56c53c2bb3ab with Lean 4.34.0; linter version unreleased (no released package). Moving route: /lean-plumb/dev/rules/PL2001/. Snapshot route for this commit: /lean-plumb/rev/56c53c2bb3ab…/rules/PL2001/. Once this commit is published, its snapshot is kept by every later deployment. See versions and evidence.

Problem. The declared Lean environment could not be loaded or identified, so the requested audit could not run. The result is INCOMPLETE, not a violation of the source.

Action. Repair the workspace so Lake can load it with its exact toolchain and dependencies, then rerun the same command.

What triggers it🔗

Setup checks load the Lake workspace, resolve dependencies to exact source states, and establish the compiler assumptions the audit needs. A failure (for example lake-workspace-load-failed when a required package directory is missing) is reported with impact incomplete.

PL2001 is also the finding for any other error that escapes the audit before a more specific rule classifies it (for example a malformed Lake query result). Read the detail: it names the failing step. Such an error is INCOMPLETE, never a pass.

Why it matters🔗

Every conformance claim is about one exact elaboration environment: toolchain, dependency revisions and source state. A result under an unknown or different environment is not evidence for the declared one.

How to fix it🔗

  1. Read the original setup error in the diagnostic detail and fix it: a missing path dependency, an unresolvable Git revision, or a toolchain that does not match lean-toolchain.

  2. Provision pinned dependencies (for example lake exe cache get for Mathlib) before auditing; provisioning is setup, not verification.

  3. Rerun the audit; a new run produces new, complete evidence.

Required proof shape🔗

No proof obligation: the rule concerns the availability of the environment. The corrected run must then pass the applicable declaration and project rules.

What a passing result establishes🔗

A passing result was produced in the declared environment: Lake loaded the workspace with the exact toolchain and resolved dependency state the result reports. An unavailable or unidentified environment is incomplete and never accepted.

It does not establish:

  • That a dependency checkout matches its recorded revision's content: dependency acquisition is a trusted mechanism.

  • Anything about the source; no declaration was inspected.

Review obligations the rule-coverage map associates with this rule (identifiers of the checker's Residual account):

  • R-QUALIFY: the checker's detection is qualified for this invocation, toolchain and capability

Every accepted result lists all residual obligations as open, whatever rules it checked: R-INTENT, R-INVARIANT, R-LAWS, R-BOUNDARY, R-NONVACUITY, R-DOC, R-COST, R-QUALIFY (and R-GRAPH for a serialized-graph claim). A listed identifier is an open obligation, never a completed review.

Every accepted result also relies on these trusted mechanisms (the checker's Trusted account), which no rule verifies:

  • toolchain: Lean elaborator, kernel and compiler at the snapshot's toolchain identity

  • acquisition: manifest parsing, Lake loading, and source, configuration and dependency acquisition

  • extraction: environment extraction, compiler and worker processes, and JSON transport

  • runtime: native runtime and every execution boundary reported as trusted

Configuration and exceptions🔗

There is no configuration that turns an incomplete setup into a pass.

Project enforcement runs through lake lint (incremental), lake lint -- --fresh and lake exe axiomGate (fresh whole-project audits from empty build output), and the build-lint policy target. See the adoption guide.
